# Running the AnonCreds v2 interop demo

This demo publishes a **real** AnonCreds v2 credential definition — produced by
[`credx`](https://github.com/hyperledger/anoncreds-v2-rs), the Rust reference
implementation — to a **live Hyperledger Fabric ledger**, revokes a holder on that
ledger, and then lets the ledger's own answer decide who verifies and who does not.

Nothing is mocked. The BBS keys, the VB20 accumulator and the presentations are genuine
credx cryptography; the network is a real four-node Fabric 2.5 deployment running the
`vdrchaincode` Java chaincode.

```
./run-anoncreds-demo.sh
```

That is the whole run. It takes about a minute on a network that is already up, or
roughly ten minutes on a cold machine that has to build the Docker images and compile
credx from source. Tear it down with `./stop-anoncreds-demo.sh`.

## 1. What you need first

### Repository layout

This repository carries the Rust demo *and* the network recipe, so the only thing it
needs from outside is the chaincode. Clone that repository in here, named exactly
`fabric-vdr-core`:

```bash
git clone https://github.com/snktibor/anoncreds-vdr-demo.git anoncreds-vdr-demo
cd anoncreds-vdr-demo
git clone https://github.com/snktibor/fabric-vdr-core.git fabric-vdr-core
```

```
anoncreds-vdr-demo/          <- you are here; run the script from this directory
├── run-anoncreds-demo.sh
├── stop-anoncreds-demo.sh
├── bootstrap.sh
├── fablo, fablo-config.json
├── Cargo.toml, src/         <- the Rust credx demo
├── docs/                    <- this walkthrough and the objects-method spec
├── target/stage3/           <- the JSON artifacts the two halves exchange
├── fablo-target/            <- generated by Fablo at first bring-up
└── fabric-vdr-core/         <- separate repo: chaincode + Java harness (gitignored here)
```

The name and the location of `fabric-vdr-core/` both matter: `fablo-config.json` deploys
the chaincode from `./fabric-vdr-core`, and Fablo resolves that against the directory
holding `fablo-config.json`.

The Java harness needs two paths that live outside its own repository — the crypto
material and this run's artifact directory. `run-anoncreds-demo.sh` exports them as
`VDR_E2E_CRYPTO_PATH` and `VDR_DEMO_STAGE3_DIR`, which Maven's forked test JVM inherits,
so nothing in `fabric-vdr-core` is configured for this layout.

### Toolchain

| Tool | Version | Why this one |
|---|---|---|
| Docker | any recent engine (verified on Docker 29.4 via OrbStack) | runs the Fabric network |

If Maven is not already on JDK 17:

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"   # macOS
export PATH="$JAVA_HOME/bin:$PATH"
```

`cargo` is found on `PATH`, or failing that at `~/.cargo/bin/cargo` (where rustup puts it
— it is often absent from a non-login shell's `PATH`).

## 2. Running it

```bash
cd anoncreds-vdr-demo
./run-anoncreds-demo.sh
```

The script fails loudly and stops at the first problem. Anything short of the final
`DEMO PASSED` banner is a failure, and the exit code is non-zero.

### What you should see, step by step

**`[0/4] Preflight`** — tool versions, then `artifact directory reset`. The script
deletes `target/stage3/` before every run so a stale report from a half-finished run can
never be mistaken for this run's result.

**`[1/4] Fabric network`** — either `resuming, not regenerating` (a few seconds) or
`clean bring-up via ./bootstrap.sh` (several minutes; see §3). Ends with:

```
    peer0.org1.example.com:7041 is serving VdrContract on my-channel1
```

That line means a read-only `listSchemas` query completed — so the peer is up, the
channel is joined, the chaincode is committed *and* the Chaincode-as-a-Service container
has connected back to the peer. It writes nothing to world state.

**`[2/4] credx`** — the Rust side runs the whole credential lifecycle off-ledger and
writes the wire bundle:

```
[emit 1/5] building the credential definition and issuing Alice and Bob
[emit 2/5] verifying both holders against the genesis accumulator in process
      Alice presentation verified: true
      Bob presentation verified: true
[emit 3/5] revoking Alice off ledger and taking the new accumulator
[emit 4/5] refreshing Bob's witness off ledger against the new accumulator
[emit 5/5] writing the wire bundle and the session state
```

**`[3/4] Java harness`** — `AnonCredsDemoIT` turns that bundle into real transactions.
This is the part that touches the ledger:

```
[harness 1/6] read <repo>/target/stage3/bundle.json (credx 691297a7…)
[harness 2/6] issuer DID published: did:vdr:01a0430c-…
[harness 3/6] schema published: …/anoncreds/v2/SCHEMA/…
[harness 4/6] credential definition published: …/PUBLIC_CRED_DEF/… (1418 bytes of publicMetadata)
[harness 5/6] revocation registry definition published: …/REV_REG_DEF/…
          publicMetadata semantically unchanged by the ledger: true
          publicMetadata byte-identical to the submitted string: true
[harness 6/6] writing 2 accumulator value(s)
          createRevRegEntry -> version 0 (genesis)
          updateRevRegEntry -> version 1 (after-alice-revoke)
```

`updateRevRegEntry -> version 1` **is** the on-ledger revocation: revoking Alice moved
the accumulator, and that new value is now the registry's committed state.

Maven should report exactly one test:

```
Tests run: 1, Failures: 0, Errors: 0, Skipped: 0 -- in com.example.vdr.e2e.demo.AnonCredsDemoIT
```

**`[4/4] credx verifies the ledger's answer`** — the payoff. The Rust side rebuilds an
`IssuerPublic` out of what `getCredDef`, `getRevRegDef` and `getRevRegEntry` returned,
using the reassembly recipe in [`anoncreds-method.md`](anoncreds-method.md) §8.1.5, and
verifies real presentations against it:

```
[verify 3/5] version-aware equality against the original IssuerPublic
      v0 byte-for-byte equal to the original: true
      v1 equal to the original with the accumulator excluded: true
      v1 accumulator replaced by the ledger's current value: true
[verify 4/5] verifying presentations against the ledger-sourced IssuerPublic
      Bob verifies at entry v0 with his genesis witness: true
      Bob verifies at entry v1 with his refreshed witness: true
[verify 5/5] negative control: revoked Alice against the ledger's v1 accumulator
      Alice rejected as expected: true
```

One line in step 2 of `verify` looks like an error and is not — it is a deliberate probe,
explained in [`README.md`](../README.md):

```
      serde_json::from_value rejected the document: invalid type: string "a1beaf99…", expected a borrowed string
      deserialized from the JSON text as IssuerPublic<BbsScheme>: true
```

The reassembly recipe has to be applied to the JSON **text**, not to an in-memory
`serde_json::Value`, because every BLS12-381 point deserializes through a path that
demands a *borrowed* `&str`. The demo runs the failing call on every verify so the
constraint stays visible instead of turning into folklore.

### Expected final output

```
==> DEMO PASSED — AnonCreds v2 revocation round-tripped through a live Fabric VDR

    schema, credential definition and revocation registry definition published on-ledger
    genesis accumulator written        -> revocation registry entry version 0
    Alice revoked off-ledger, published -> revocation registry entry version 1
    IssuerPublic reassembled from getCredDef + getRevRegDef + getRevRegEntry (spec 8.1.5)
    Bob accepted at v0 (genesis witness) and at v1 (refreshed witness)
    revoked Alice REJECTED against the ledger's current accumulator
```

### Artifacts

Everything lands in `target/stage3/` (gitignored, regenerated on every run):

| File | Written by | Contents |
|---|---|---|
| `bundle.json` | `cargo run -- emit` | what credx published, in the §8.1.6 wire shape |
| `session.json` | `cargo run -- emit` | the credx state the verification is judged against; no issuer secret keys |
| `vdr-report.json` | `AnonCredsDemoIT` | what the ledger returned, including the entry history |

## 3. The network: clean start vs. resume

**This is the one thing most likely to trip you up, so the script handles both cases.**

`./bootstrap.sh` is the documented bring-up, and it only works on a network that does not
exist yet. On a network that was merely *stopped* — `fablo stop`, a Docker restart, a
reboot — it fails:

```
Can't generate certs, directory already exists : .../crypto-config/peerOrganizations/orderer.example.com
```

That refusal is correct, not a bug: `bootstrap.sh` calls `fablo up`, whose first act is to
regenerate crypto material, and overwriting the identities the running ledger already
trusts would break the network rather than restore it.

The recovery is a different pair of commands:

```bash
./fablo start
docker start $(docker ps -aq --filter 'name=ccaas_.*_vdrchaincode_')
```

The second line is not optional. `fablo start` is a plain `docker compose up -d` over
`fablo-target/fabric-docker/docker-compose.yaml`, and the two `ccaas_*` chaincode
containers are **not in that compose file** — Fablo launches them with `docker run` during
its chaincode install step. Skip the `docker start` and the peers come up healthy while
every transaction fails to endorse.

The script picks between the two paths automatically, and the test it uses is exact:

| `fablo-target/fabric-config/crypto-config` | State | What the script runs |
|---|---|---|
| absent | never generated, or destroyed by `fablo down` | `./bootstrap.sh` (**clean**) |
| present | generated before, network stopped or running | `./fablo start` + `docker start ccaas_*` (**resume**) |

That discriminator is reliable because `fablo down` deletes the directory and `fablo stop`
does not.

Either way the script then polls a read-only chaincode query for up to 180 s before
continuing, so a resumed network is never handed to the harness before the CCaaS container
has reconnected.

**If the network is damaged** — the probe times out, containers were removed by hand,
world state is inconsistent — rebuild it from scratch:

```bash
./bootstrap.sh reset     # tear down and bring up again, keeping the configuration
```

## 4. Teardown

```bash
./stop-anoncreds-demo.sh                   # stop the network, delete target/stage3/
./stop-anoncreds-demo.sh --keep-artifacts  # stop, but keep the JSON artifacts to inspect
./stop-anoncreds-demo.sh --down            # destroy the network entirely
```

The default is a **stop**: containers and ledger state survive, so the next
`./run-anoncreds-demo.sh` resumes in seconds. `--down` runs `fablo down`, which removes
the generated crypto material and world state — the next run then takes the clean path and
rebuilds everything.

Like the runner, the teardown stops the `ccaas_*` containers explicitly, because
`fablo stop` does not reach them either.

## 5. Why the Maven invocation looks the way it does

The script runs the harness with:

```bash
mvn verify -Dit.test=AnonCredsDemoIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false
```

**Do not replace this with `-DskipTests`.** The obvious-looking

```bash
mvn verify -Dit.test=AnonCredsDemoIT -DskipTests     # WRONG — runs nothing
```

is a **false green**. `maven-failsafe-plugin` binds its own `skipTests` parameter to the
same `${skipTests}` property that surefire uses, so the flag meant to silence the 121 unit
tests silences the integration test too. The build reports `BUILD SUCCESS` having executed
nothing at all — no test, no transaction, no ledger write, no `vdr-report.json`. Verified
against this project: with `-DskipTests` the log contains no `Tests run:` line whatsoever
and Maven still exits 0.

The three flags that do work:

| Flag | Effect |
|---|---|
| `-Dit.test=AnonCredsDemoIT` | overrides failsafe's default includes, so `RunCucumberIT`'s 20 scenarios do not also run |
| `-Dtest=none` | surefire matches no unit test |
| `-Dsurefire.failIfNoSpecifiedTests=false` | …and does not fail the build for having run none |

Failsafe's own `failIfNoSpecifiedTests` is left at its default of `true`, which is a free
safety net: if `-Dit.test` ever stops matching — a rename, a typo — the build fails loudly
instead of silently running zero integration tests.

The script does not take Maven's word for it either. After the harness step it checks that
`vdr-report.json` exists *and* is newer than `bundle.json`, so a Maven invocation that
exited 0 without running the test is caught independently.

Two related notes, in case you go looking:

- The `e2e` Maven profile is inert. `pom.xml` sets `<surefire.skip>true</surefire.skip>`,
  but surefire 3.2.5 has no `${surefire.skip}` binding, so `mvn -Pe2e verify` still runs
  all 121 unit tests. It is harmless, just not load-bearing.
- `TransactionExecutor.submit` **swallows** transaction failures into a `ScenarioContext`
  rather than throwing. `AnonCredsDemoIT.requireCommitted` therefore checks
  `lastTransactionException()` after every single write; without it the harness would sail
  past a transaction that never committed and "pass" while having written nothing.
- A plain `mvn verify` in `fabric-vdr-core` now runs `AnonCredsDemoIT` **as well as**
  `RunCucumberIT`, because the class name matches failsafe's default `*IT` include. That
  means the ordinary build wants both a live network and a `bundle.json` to read. Run it
  from a shell where `VDR_E2E_CRYPTO_PATH` and `VDR_DEMO_STAGE3_DIR` are set — or just run
  `./run-anoncreds-demo.sh`, which sets them and runs `cargo run -- emit` first. Without
  them it stops at
  `No bundle at … — run 'cargo run -- emit' in anoncreds-vdr-demo first`.

## 6. Verifying that failure actually fails

The demo is only worth anything if a broken run is loud. It is, and the chain is easy to
check end to end. `AnonCredsDemoIT` accepts an artifact-directory override
(`VDR_DEMO_STAGE3_DIR`, or `-Dvdr.demo.stage3Dir`), and the runner only *defaults* that
variable — one already set in the environment wins. So point it at a bundle with a
corrupted revocation key:

```bash
mkdir -p /tmp/badstage
python3 - <<'PY'
import json
d = json.load(open("target/stage3/bundle.json"))
d["revRegDef"]["publicKeys"]["revocationVerifyingKey"] = "deadbeef"
json.dump(d, open("/tmp/badstage/bundle.json", "w"), indent=2)
PY

VDR_DEMO_STAGE3_DIR=/tmp/badstage ./run-anoncreds-demo.sh; echo "exit: $?"
```

The chaincode rejects the key, `TransactionExecutor.submit` swallows the endorsement
error, `requireCommitted` catches it and throws, and the failure propagates all the way
out:

```
java.lang.IllegalStateException: createRevRegDef did not commit: chaincode response 500,
  publicKeys.revocationVerifyingKey must be a compressed BLS12-381 G2 point as exactly
  192 lowercase hex characters
[ERROR] Tests run: 1, Failures: 0, Errors: 1, Skipped: 0
[INFO] BUILD FAILURE

!! FAILED: publishing to the VDR (AnonCredsDemoIT) (exit status 1)
!! The demo did NOT complete. Do not read anything above as a pass.
exit: 1
```

(You need a valid `bundle.json` to corrupt, so run the demo successfully once first.)
